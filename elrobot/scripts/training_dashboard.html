Action error and validation

Prefer a sustained decline in validation loss. Training L1 and validation use different latent behavior; compare their trends, not their absolute gap.

Training loss components

Total training loss = L1 action error + 10 × KL regularization for this ACT configuration. KL is not a motor-position error.

Gradient norm

Check sustained spikes together with worsening loss. Non-finite values need investigation; there is no universal good gradient threshold.

Training throughput

Samples per second for training updates. Validation and checkpoint saving add pauses that this metric does not fully capture.

Time per update and data load

Seconds per training update/window. If data loading consistently dominates, inspect the data pipeline before changing the policy.

GPU memory allocated

Trainer-reported allocation in GB, not total GPU usage or free memory. Watch training logs for CUDA out-of-memory errors.

What to monitor

  • Both losses improving: continue the planned run. A few noisy evaluations are normal.
  • Training improves while validation worsens repeatedly: possible overfitting. Compare earlier saved checkpoints; do not automatically choose the final model.
  • Both flatten: more updates may add little. Review demonstration quality and task-phase errors before changing several settings.
  • Startup checks: this run should report 2,408 training frames and 723 validation frames. Both cameras are 224×224; top is already cropped in the prepared dataset.
  • Interpretation: there is no universal good loss threshold. Normalization/splits differ between runs, so raw losses are not directly comparable across datasets. Low offline loss does not establish successful cheese placement.
  • Coverage: these logs contain aggregate errors, not per-joint or grasp/release accuracy. The dashboard does not run a model, evaluate task success, or control hardware.
